The Ethicstech IoT Gateway Lite exposes a single web interface over both Wi-Fi and Ethernet. The firmware runs two servers on port 80: an Arduino `WebServer` for Wi-Fi clients (`initWebServer()` L7396) and a hand-rolled `EthernetServer` router inside `webServerTask` (L132) for Ethernet clients. Both share the same HTML pages, but their route coverage and behavior differ in several ways.

## Authentication model

A single global boolean `isAuthenticated` controls access for every client on both interfaces. Once any user logs in successfully, all subsequent requests from any IP on Wi-Fi and Ethernet are treated as authenticated until `/logout` or a reboot clears the flag.

<Warning>
  There are no sessions, cookies, tokens, or per-client state. Logging in from one browser authenticates every other client on the network as well.
</Warning>

Credentials are compared in plaintext and stored in plaintext in `/login.json`. The login failure message explicitly reveals whether the username or password was wrong.

## Config mode and backend pause

Any web activity on Wi-Fi or Ethernet sets `wifiConfigMode` or `ethernetConfigMode` and records `lastWebActivity` via `recordWifiActivity()` (L121). When config mode is active, `backendTask` discards the current data payload and pauses all collection and transmission for 30 seconds after the last web request (L569). This prevents collisions between configuration writes and data transmissions, but it also means data is lost while you browse the UI.

  Ethernet does **not** serve `/network_status`, `/io_status`, `/modbus_status`, `/latestdata.json`, `/manual.pdf`, `/update`, `/reset`, or `/set_auto_ota`. Status widgets and auto-OTA toggles that rely on these routes will not work over Ethernet.
</Info>

## Wi-Fi vs Ethernet differences

| Behavior | Wi-Fi (`WebServer`) | Ethernet (`EthernetServer`) |
| --- | --- | --- |
| Auth enforcement | `handleProtectedPage` wrapper | Inline rewrite to `/login` |
| POST body parsing | `server.arg()` | `getPostBody()` + `getFormValue()` |
| Response chunking | Standard HTTP | 512-byte chunks (ENC28J60 buffer limit) |
| SPI mutex | Not needed | `ethernetSpiMutex` taken per client |
| Unknown path | Redirect to login or `handleNotFound` | Returns home page |
| Modbus save validation | 32-device limit, duplicate-register check | No limits, no duplicate check |
| Network settings save | Copies `settings_s`, then `saveSettings()` | Only overwrites non-empty fields (`saveNetworkSettingsFromBody`) |
| Protocol numeric fields | Parsed with `toInt()` from `server.arg()` | Parsed with `toInt()` even if missing (becomes 0) |
| FTP fields on servers form | Only saved when `Set_FTP` is checked | Same |

## Save-then-reboot pattern

Every configuration POST handler calls `saveSettings()`, `saveConfig()`, `saveServerconfig()`, or `saveModbusDevice()` and then returns a styled confirmation page with two buttons: **Back** (to continue editing) and **Reboot Now** (to `/reboot?now=1`). The settings structs used by the runtime (`settings`, `mbConfig`, `modbusDevices`) are only copied from their shadow counterparts (`settings_s`, `mbConfig_s`, `modbusDevices_s`) during boot load, so changes do not take effect until after a reboot.

The servers (`servers`) and login (`login`) structs are edited live or saved immediately, so NTP/FTP and credential changes apply without a reboot.

## Security properties

The following security characteristics are implemented as a consequence of the current code, not as recommended practices:

- **No HTTPS / TLS on either interface.** All traffic is plain HTTP.
- **No CSRF tokens.** Any authenticated client can POST forms on behalf of another.
- **No rate limiting.** Login and reset pages can be brute-forced.
- **Plaintext credential storage.** `/login.json` stores the password in plain text.
- **Global auth flag.** One successful login authenticates all clients on Wi-Fi and Ethernet simultaneously.
- **Unauthenticated POST `/update`.** Anyone on the Wi-Fi network or AP can flash firmware without logging in.
- **Unauthenticated GET `/set_auto_ota`.** Auto-OTA state and company name can be changed by any client.
- **Unauthenticated `/reset`.** The factory PIN reset page is public; the PIN is hard-coded in `definitions.h` (`RESET_PIN`).
- **Default credentials.** Factory defaults include a hard-coded default STA password and `admin/admin` login.
